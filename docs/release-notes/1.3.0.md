# 1.3.0 — typed capabilities

Version 1.3.0 makes the capabilities of a data source **part of its type**.
Until 1.2.0 `IDataSource<TItem>` promised nothing about its extensions: a
consumer discovered them at runtime with `getExtension(Class)` and
`instanceof`, imported the concrete classes to probe them, and failed on
mount when the one it needed was missing. Now a source built with
`createDataSource(reader, { filtering, pagination })` is an
`IDataSource<User, "filtering" | "pagination">`, a consumer declares what it
needs in a signature (`source: IDataSource<User, "filtering">`) and the
compiler checks it.

The release is additive: new exports, two deprecations, no removed or changed
signature. `read()`, the events and everything under `query-items` keep their
semantics.

## 1. What's new

### 1.1 The capabilities map

`DataSourceCapabilities<TItem>` maps a **key** to the **interface** of the
extension a source may expose; `DataSourceCapability` is a key of it. The
keys are the interfaces, not the classes: a `FilterExtensionWithFixedFilters`
is a `filtering`, a `SingleSortExtension` is a `sorting`.

```typescript
interface DataSourceCapabilities<TItem = Any> {
  filtering: IFilterExtension<TItem>;
  pagination: IPaginationExtension<TItem>;
  projection: IProjectionExtension<TItem>;
  sorting: ISortExtension<TItem>;
}
type DataSourceCapability = keyof DataSourceCapabilities;
```

The interface is open: a consumer augments it to add its own keys
([1.6](#16-custom-extensions-and-augmentation)).

### 1.2 IDataSource<TItem, TCaps>

`IDataSource` gains a second type parameter, the keys it guarantees:

```typescript
type IDataSource<TItem = Any, TCaps extends DataSourceCapability = never> =
  IDataSourceBase<TItem> &
  Readonly<Pick<DataSourceCapabilities<TItem>, TCaps>> &
  Readonly<Partial<Omit<DataSourceCapabilities<TItem>, TCaps>>>;
```

- Every key in `TCaps` is a **required** readonly property; every other known
  key is an **optional** one to narrow on: `IDataSource<User, "filtering" |
  "pagination">` has `filtering` and `pagination` for sure, and `sorting?` /
  `projection?` to check with `if (source.sorting) ...`.
- Assignability follows from the structure: a source with more capabilities
  fits a parameter asking for fewer (`IDataSource<User, "filtering" |
  "pagination">` → `IDataSource<User, "filtering">` → `IDataSource<User>`);
  the opposite direction is a compile error.
- The default `TCaps = never` guarantees nothing, which is what a plain
  `IDataSource<User>` always meant: **every existing annotation keeps
  compiling**, with the four keyed properties now available as optional ones.

`IDataSource` is now a **type alias** (an intersection) instead of an
interface: TypeScript does not let an interface extend a `Pick` over a generic
key. Nothing changes for an annotation, an import or an `implements
IDataSource<User>` with concrete type arguments; only a declaration merging on
`IDataSource` would stop working. The members that do not depend on the
capabilities (`items`, `isReading`, `read()`, `getExtension`) live in the new
interface `IDataSourceBase<TItem>`.

### 1.3 createDataSource

`createDataSource(reader, extensions, others?)` is the public way to build a
source: it infers `TCaps` from the record of extensions, which a class
constructor cannot do reliably.

```typescript
function createDataSource<TItem, TExt extends DataSourceExtensions<TItem>>(
  reader: DataSourceReader<TItem>,
  extensions: TExt,
  others?: List<IDataSourceExtension<TItem>>,
): IDataSource<TItem, DefinedCapabilities<TExt>>;
```

`DataSourceExtensions<TItem>` is `Partial<DataSourceCapabilities<TItem>>`, the
record by key. `DefinedCapabilities<TExt>` are the keys of the record that are
known capabilities **and whose value type does not admit `undefined`**: a key
that may be `undefined` is exposed when set, but it is not a capability of the
type.

```typescript
const users = createDataSource(readUsers, { filtering, pagination });
// IDataSource<User, "filtering" | "pagination">
users.filtering.addFilter(adult);

const maybeSorting: SortExtension<User> | undefined = sortable ? new SortExtension<User>() : undefined;
const products = createDataSource(readProducts, { filtering, sorting: maybeSorting });
// IDataSource<Product, "filtering">
if (products.sorting) products.sorting.addSort(byName);
```

The record is checked against the interfaces: `{ filtering: sorting }` or a
pagination of another item type is a compile error.

### 1.4 The canonical pipeline order

The order of the pipeline is now a fact of the library, exposed as
`DataSourceCapabilitiesOrder`: `filtering`, `sorting`, `pagination`,
`projection`, then the extensions given as `others` in array order, then the
augmented keys in insertion order of the record. Whatever the key order you
write, the count reader of the pagination receives the filters and the sorts,
and the hash it watches for the page reset covers them. The README no longer
asks you to put the `FilterExtension` before the `PaginationExtension`.

The hooks of the extensions, the reader and the signal are invoked exactly as
in 1.2.0, in that order.

### 1.5 The class

`DataSource<TItem, TCaps extends DataSourceCapability = never>` exposes the
four keyed properties (`filtering`, `pagination`, `projection`, `sorting`) as
**own** readonly properties, set only when the extension is given: `"sorting"
in source` is `false` for a source without sorting, and `source.sorting` is
`undefined`. The constructor is
`new DataSource(reader, extensions?, others?)`, where `extensions` is:

- the **record** by key (`DataSourceExtensions<TItem>`): the pipeline is built
  in the canonical order;
- a **list** of extensions (**deprecated**, removed in 2.0): it runs in array
  order as in 1.2.0, and the keyed properties are filled by `instanceof` on
  the classes of the package (a `FilterExtensionWithFixedFilters` fills
  `filtering`, a `SingleSortExtension` fills `sorting`; the first instance
  wins, as in `getExtension`), so existing code gets `filtering` /
  `pagination` / ... for free.

`others`, new and optional, are the extensions without a key, run after the
keyed ones (after the list, with the list form). `getExtension(Class)` keeps
working on both forms and on `others`; `dispose()` disposes every extension,
keyed or not.

The class cannot infer `TCaps` from its arguments: `new DataSource<User>(...)`
guarantees nothing (its keyed properties are typed as possibly `undefined`),
`new DataSource<User, "filtering">(reader, { filtering })` states them by
hand. Since a class cannot pick its members from a generic key either, the
keyed properties are typed through `DataSourceCapabilityProperty<TItem,
TCaps, TKey>` (the extension when `TKey` is in `TCaps`, the extension or
`undefined` otherwise) and the class implements `IDataSource<TItem>`; for
every concrete `TCaps` a `DataSource<TItem, TCaps>` is structurally an
`IDataSource<TItem, TCaps>`, as the type specs check. Annotate with
`IDataSource`, never with this helper.

The base class of the package extensions, `DataSourceExtension`, moved from
`data-source/models.ts` to its own folder `data-source/extension/` (with
`DataSourceExtensionOptions` and `DataSourceExtensionChangeDelayDefault`), so
that `DataSource` can import the four classes of the package without a cycle
between the base class and its subclasses. The exports are unchanged.

### 1.6 Custom extensions and augmentation

A custom extension has two homes:

- in `others`, untyped, run after the known extensions:

  ```typescript
  const users = createDataSource(readUsers, { filtering, pagination }, [
    new DistinctExtension<User>(),
  ]);
  ```

- under a key of its own, by augmenting the map, so that it is a capability
  like the others (type, keyed property, assignability):

  ```typescript
  declare module "@mantlebee/ts-data" {
    interface DataSourceCapabilities<TItem> {
      distinct: DistinctExtension<TItem>;
    }
  }
  const users = createDataSource(readUsers, { filtering, distinct });
  // IDataSource<User, "filtering" | "distinct">
  users.distinct; // DistinctExtension<User>
  ```

Augmented keys run after the known ones and after `others`, in insertion
order of the record.

### 1.7 Semantics

- The keyed properties of a source are the very instances given, set only
  when given: `key in source` tells whether the capability is there.
- A record key set to `undefined` is absent: no property, nothing in the
  pipeline, not a capability of the type.
- The pipeline order is canonical: `filtering`, `sorting`, `pagination`,
  `projection`, `others`, augmented keys.
- The list form of the constructor keeps the array order and fills the keyed
  properties by `instanceof`, the first instance of each class winning.
- `getExtension` searches the whole pipeline (keyed, `others`, augmented).
- `dispose()` disposes every extension of the pipeline.
- `read()`, `isReading`, `items`, the events and the latest-read-wins
  behaviour are those of 1.2.0.

### 1.8 Exports

New:

- `createDataSource` (`data-source/utils.ts`)
- `DataSourceCapabilities`, `IDataSourceBase` (`data-source/interfaces.ts`)
- `DataSourceCapability`, `DataSourceCapabilityProperty`,
  `DataSourceExtensions`, `DefinedCapabilities` (`data-source/types.ts`)
- `DataSourceCapabilitiesOrder` (`data-source/models.ts`)

Changed without breaking: `IDataSource` is a type alias with a second,
defaulted type parameter; `DataSource` has a second, defaulted type parameter,
accepts the record (or the list) and a third optional argument `others`, and
exposes `filtering`, `pagination`, `projection`, `sorting`.

## 2. Deprecations

Both are removed in **2.0**:

- `IDataSource.getExtension(Class)` / `DataSource.getExtension(Class)`: read
  the keyed property instead (`source.filtering`, `source.pagination`,
  `source.projection`, `source.sorting`, or an augmented key). It needs no
  class import, no type argument and no `instanceof`.
- `new DataSource(reader, [extension, ...])`, the list form of the
  constructor: pass the record (`{ filtering, pagination }`), or better build
  the source with `createDataSource`.

## 3. Upgrading

```bash
npm install @mantlebee/ts-data@^1.3.0
```

Nothing is required: every 1.2.0 program compiles and behaves the same. To
benefit from the typing:

1. Build the sources with `createDataSource(reader, { filtering, pagination, ... })`
   instead of `new DataSource(reader, [filtering, pagination, ...])`; drop
   any ordering done by hand, the library orders the pipeline.
2. Replace `source.getExtension<FilterExtension<User>>(FilterExtension)` with
   `source.filtering` (`PaginationExtension` → `pagination`, `SortExtension` /
   `SingleSortExtension` → `sorting`, `ProjectionExtension` → `projection`).
   Where the source may lack the extension, narrow: `if (source.sorting)`.
3. Declare what a consumer needs in its signature,
   `source: IDataSource<User, "filtering" | "pagination">`, and let the
   compiler reject a source that cannot do it, instead of throwing at runtime.
4. Give a custom extension a key by augmenting `DataSourceCapabilities`, or
   pass it in `others`.
